# 데이터베이스 설계 및 API 아키텍처 명세서

## 1. 개요

본 문서는 핀테크 송금 및 계좌 관리 서비스의 핵심 데이터베이스 스키마, 엔티티 관계, 그리고 REST API 명세 초안을 정의합니다.

본 설계는 데이터 무결성, 트랜잭션 안정성, 동시성 제어를 중심으로 작성되었습니다.

---

## 2. 데이터베이스 스키마 및 ERD 설계

### 2.1 핵심 엔티티 및 관계

- **User (1) ─── (N) Account:** 한 명의 사용자는 여러 개의 금융 계좌를 소유할 수 있습니다.
- **Account ─── Transaction:** 모든 입금 및 송금 내역을 외래키 매핑을 통해 추적합니다.

### 2.2 엔티티 상세 스펙

- **User (회원)**
    - `id` (기본키, Long)
    - `email` (이메일, 고유값)
    - `password` (비밀번호)
    - `name` (이름)
- **Account (계좌)**
    - `id` (기본키, Long)
    - `user_id` (외래키, Long)
    - `account_number` (계좌번호, 고유값)
    - `balance` (잔액, BigDecimal) - 동시성 제어의 핵심 대상
- **Transaction (거래 내역)**
    - `id` (기본키, Long)
    - `sender_account_id` (외래키, Long, 허용값 Null - 입금 시 미사용)
    - `receiver_account_id` (외래키, Long)
    - `amount` (거래 금액, BigDecimal)
    - `type` (거래 유형: 입금, 송금)
    - `created_at` (생성 일시)

---

## 3. 설계 의사결정 및 근거

- **User와 Account의 분리:** 사용자 프로필 관리와 금융 계좌 상태 관리의 책임을 분리하여, 향후 다중 계좌 확장성을 확보했습니다.
- **동시성 제어 및 트랜잭션 관리 확보:** 다수의 사용자가 동시에 충전 및 송금을 요청할 때 발생할 수 있는 데이터 경합(Race Condition)을 방어하기 위해, 엄격한 트랜잭션 관리와 동시성 제어(비관적/낙관적 락 또는 Redis 분산 락) 적용을 염두에 두고 설계했습니다.
- **Transaction 내 복수 외래키 채택:** 보낸 계좌와 받는 계좌를 동시에 두어 P2P 송금의 자금 흐름 방향성을 명확하게 표현했습니다.

---

## 4. REST API 명세 초안

### 4.1 회원 및 인증

- **회원가입:** `POST /api/v1/users`
- **로그인:** `POST /api/v1/auth/login` *(시큐리티 및 토큰 인증 적용 검토)*

### 4.2 계좌 및 잔액

- **계좌 생성:** `POST /api/v1/accounts`
- **잔액 조회:** `GET /api/v1/accounts/{accountId}`

### 4.3 입금 및 송금 (핵심 챌린지)

- **계좌 충전:** `POST /api/v1/accounts/{accountId}/deposits` *(동시성 제어 적용 포인트)*
- **계좌 송금:** `POST /api/v1/transfers` *(동시성 이슈 방어 및 락/분산 락 핵심 적용 대상)*

### 4.4 거래 내역 조회

- **거래 내역 페이징 조회:** `GET /api/v1/accounts/{accountId}/transactions?page=0&size=20`

---

## 5. 주요 예외 상황 처리 전략

- **입력값 및 클라이언트 오류:** 중복 이메일, 잘못된 로그인 정보, 존재하지 않는 계좌 및 사용자, 0 이하의 금액 요청
- **비즈니스 및 상태 오류:** 잔액 부족, 자기 자신에게 송금 시도, 인증되지 않은 사용자 접근
- **동시성 오류:** 다중 접속 환경에서의 충전 및 송금 시 데이터 경합 발생 상황.
